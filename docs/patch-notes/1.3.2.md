# Cookie Jar 1.3.2

- Date: 2026-11-15
- Platform: Windows

## Briefing

Restore working multi-instance launches so new accounts no longer close open games

## Changes

- Stop holding `ROBLOX_singletonMutex` and `ROBLOX_singletonEvent` for the launcher's lifetime. Since 1.3.0, each new client took Roblox's single-instance path and ended the older games. The same Roblox build ran 5-7 clients under 1.2.2, so this was a Cookie Jar regression, not a Roblox change.
- Restore the 1.2.2 method: after each account client starts, Cookie Jar polls it and closes its singleton handles. The website (browser) launch path does the same for each new client it detects.
- If the started player hands off to exactly one new RobloxPlayerBeta process, Cookie Jar now tracks that process instead of failing the launch.
- Launch-failure messages now name the PID that exited and no longer tell users to update Roblox. The log records which existing client closed during which launch.

## Source

- `src/LaunchEnvironment.cs`: preparation no longer reserves the guard; adds the `CloseSingletons(pid)` boundary.
- `src/InstanceManager.cs`: per-client singleton closing in `LaunchAccount` and `WatchLoop`, hand-off following and clearer failure messages.
- `tests/LaunchPipelineTests.cs`: checks that the new client's PID has its singleton handles closed.

## Validation

- `./build.ps1`: Windows build and release check passed.
- `./tests/build_launch_tests.ps1`: 94 checks passed (simulated players only; no real Roblox).
- `./tests/build_diagnostic_tests.ps1`: 34 checks passed.
- No live Roblox multi-account test was run.

## Known limitations

- `src/MultiInstanceGuard.cs` remains in the code (and its isolated tests) but is no longer used for launches.
- Hand-off following is skipped when more than one unknown player appears at once.
